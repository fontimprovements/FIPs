# FIP001 — Path boolean subtraction

Non-destructive outline subtraction on source paths. A closed path marked as
a **subtraction cutter** punches a hole in everything **below** it in the
layer’s shape list. Paths and components share that list: their relative order
is the stacking order. The cutter itself is omitted from the compiled outline.

## Motivation

Type designers often need a hole that stays editable: an accent that cuts a
bowl, a counter drawn as a cutter instead of a reverse-winding contour, a
slash that punches `o` after the `o` is placed as a component.

Today that usually means destructive booleaning, or relying on winding
direction inside a single compound path. Those approaches lose the cutter as
an object, and they do not say how a cutter on a **component** should interact
with paths on the **host** glyph.

This FIP stores a small flag on the cutter path and defines a single stacking
rule so editors, interpolators, and compilers agree.

## Storage

On each cutter **path** (not on the glyph, not on the font):

| Key | Value |
| --- | --- |
| `fip001-boolean` | `"subtraction"` |

Other values for `fip001-boolean` are reserved. Absence of the key means the
path is additive (ordinary fill).

### Format mapping

Source formats should round-trip the key on the path object:

- **Glyphs** (`.glyphs` / `.glyphspackage`): path `attr["fip001-boolean"] =
  subtraction`. Implementations may also keep a vendor-neutral copy on the
  unified path record (`format_specific["fip001-boolean"]`) when they use an
  intermediate model.
- **UFO / Designspace, Babelfont JSON, FontLab VFJ**, and similar: the same
  key on the path’s custom / format-specific dictionary.

The flag is per path, per layer. Linked or intermediate layers that share
shape indexes should carry the same flag at those indexes if the designs are
meant to interpolate.

Background / non-export layers are not compiled; this FIP does not require
processing them.

## Shape list and stacking order

A layer is an **ordered list of shapes**. Each shape is either a path or a
component. That list is the z-order:

- **Earlier** in the list = **below** (drawn first; subject to later cutters).
- **Later** in the list = **above** (drawn last; covers holes left by earlier
  cutters).

Paths and components are **not** two separate stacks. A component between two
paths sits between those paths. Reordering shapes (bring forward / send
backward, and so on) changes the boolean result.

```
layer.shapes (bottom → top)
  [0] path A          additive
  [1] component "o"   expands to o's shapes, still in this slot
  [2] path B          subtraction  → cuts A and the flattened "o"
  [3] path C          additive       → sits on top of the hole
```

### Flattening components

Compile-time processing sees **paths only**. Before subtraction:

1. Identify every glyph whose own paths **or** whose **component tree**
   contains at least one subtraction path (recursive: a host that only
   references a cutter glyph still counts).
2. **Decompose** those glyphs (and only those) so each component is replaced
   **in place** by the referenced glyph’s shapes, with the component transform
   applied. Nested components expand the same way.
3. The result is one flat path list per layer. Relative order is preserved:
   everything that lived inside a component stays together where that
   component sat among its siblings.

After flatten, a cutter that lived **inside** a component still only cuts
what appears **before** it in this flat list: earlier paths of that same
component, plus earlier sibling shapes of the host. It does **not** cut host
paths that were listed **after** that component.

```
Host glyph "oslash"
  [0] component "o"          → o's bowl (additive)
  [1] path slash             subtraction

Flattened:
  [0] o bowl
  [1] slash (cutter)         cuts the bowl
  compiled: o with a slash-shaped hole; slash omitted

Host glyph "oslashacute"
  [0] component "oslash"     tree contains a cutter → whole glyph decomposes
  [1] component "acute"

Flattened (illustrative):
  [0] o bowl
  [1] slash (cutter)         cuts the bowl only
  [2] acute paths            sit on top of the hole
```

A cutter on the host that is listed **before** a component does **not** cut
that component: the component’s paths appear later and cover the hole.

```
  [0] path cutter            subtraction  → nothing below (no-op as a cut)
  [1] component "o"         o remains intact on top
```

### Sequential difference

On the flattened closed paths, walk **bottom to top**:

1. Additive closed paths accumulate as the current subject.
2. When a **closed** subtraction path is reached, replace the subject with
   **NonZero difference**: `subject − cutter`. The cutter is **not** appended
   to the subject.
3. Additive paths **after** that cutter start a new top group: they are not
   subtracted by that cutter and cover the hole.
4. Open paths are never cutters. They are left as-is and are not part of the
   filled boolean subject. Implementations may omit open paths from the
   compiled filled outline (same as typical TrueType/CFF export).

Several cutters apply in order. Two cutters with an additive between them: the
first cuts everything below it; the additive covers that hole; the second
cuts that additive (and any remainder below that still overlaps).

Fill rule: **NonZero** (not even-odd). Winding of the cutter still matters for
the difference engine; reversing a cutter is a geometric edit, not a
substitute for the flag.

The compiled binary font contains only the resulting additive contours. It
does not need to store `fip001-boolean`.

## Source vs preview

Editors should keep original nodes. Live preview should match the compiled
coverage:

- Additive fill only where the compiled outline has ink.
- A cutter above a solid punches that solid; the cutter’s **preview** fill
  may cover the hole (the cutter is not in the binary).
- An additive **above** a cutter covers the hole, as in the binary.

Interpolation and VF compatibility: glyphs that participate in this filter
are fully decomposed at compile, so variable-component (`VARC`) packing does
not apply to them. Glyphs with no cutter in their tree keep components.

## Example (same-glyph paths)

Four closed rectangles, bottom to top: large additive, small cutter in the
middle, small additive overlapping the hole, distant additive that does not
overlap the cutter.

- The cutter differences the large rectangle.
- The overlapping additive after the cutter fills the hole locally.
- The distant additive is unchanged (no overlap with the cutter).

See `example.py` for the walk, including a component slot expanded in place.

## Out of scope

- Intersection / clip (keeping only the overlap). A future FIP or another
  `fip001-boolean` value could define that; this document specifies only
  `"subtraction"`.
- Changing how overlapping additive paths combine in the **absence** of a
  cutter (existing NonZero / even-odd fill of the font format).
- Hinting, overlapping-path cleanup unrelated to this flag, or UI.

## Reference notes

A complete geometry implementation can use a robust path boolean (for
example Linesweeper `binary_op` with `FillRule::NonZero` and
`BinaryOp::Difference`). Editors may approximate the same coverage on a
canvas (destination-out of fills below a cutter; later additives drawn on
top) without rewriting source nodes.

Counterpunch implements this FIP in source, preview, Glyphs round-trip, and
compile. Other tools should treat the key as vendor-neutral.
